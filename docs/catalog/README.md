### Adding one editorial draft

1. Select an existing `sourceId` from the reference manifest (for example `kt-127`) and add **one** matching record to `reference-overrides.json`. Use a unique lowercase hyphenated `slug`. Do not add an item the source inventory does not contain.
2. Supply original `copy.en` and `copy.ro` with `name`, `summary`, `description` for **both** locales, or leave them `null` while researching. The fields contain authored BODICH explanations, not published seller text. Keep real model/brand attribution and Romanian diacritics; do not assert a BODICH-manufactured model.
3. Add specifications only when verified: `specs: [{ "kind": "thrust", "value": 100, "unit": "N", "sourceUrl": "https://…", "verifiedOn": "YYYY-MM-DD" }]` illustrates the **shape**, not an actual turbine specification. Each value must have evidence, a permitted unit for its kind, and a real, non-future UTC verification date in `YYYY-MM-DD`. A matching date string without a valid calendar date is not accepted. Never invent missing thrust, speed, battery, or pump compatibility.
4. Stage prospective **original** images under `docs/catalog/draft-assets/<source-id-lowercase>/` (outside `public/`), where `<source-id-lowercase>` equals the exact source ID converted to lowercase (important for opaque Square IDs). Paths for another product's ID are rejected. An `images` entry requires `path`, `kind` (`original_concept`, `original_diagram` or `product_photo`), `rights` (`pending`, `cleared`, `rejected`), EN/RO `alt`, and pixel `width`/`height`. Concept visuals must be explicitly labeled and must not pass as accurate physical product photography. `company_approved` drafts cannot contain images without `rights: "cleared"`.
5. Run `npm run catalog:source:check` and `npm run check`. The offline checks reject lost/duplicate source IDs, duplicate slugs, unknown source/item types, unknown keys, incomplete translations, bad units/provenance, unsafe asset paths (including images in another product's directory), invalid/future verification dates and uncleared images on approved drafts. Self-tests cover every item type, the digital service, collection tagging, and negative examples.
6. An authorized reviewer must verify source identity, originality, bilingual copy, usage rights, and applicability to **BODICH's** own catalog. Setting `approval: "company_approved"` in research data **does not publish anything**. Publication remains an explicit, separately reviewed change to `confirmedProducts` in `src/catalog/data.ts`, using its stricter manufacturer/evidence/asset checks.

**Publication invariant:** Draft/reference entries never generate public EN/RO routes, product cards, SEO metadata or image files. The public `ProductCard` and `ProductPage` are explicitly typed to `ConfirmedCatalogProduct`, have no cart/checkout controls, and display an unconfirmed-details notice rather than inventing stock or performance. Keep `public/images/catalog/` limited to files referenced by approved confirmed product records. This separation must remain intact during import issues #27–#34. CI now scans `src/` imports (including ordinary, re-export, side-effect and dynamic literal imports) to reject direct imports of the unpublished `reference.ts` module or source/edit JSON manifests. It allows the offline validator under `scripts/` to inspect these inputs. This guard targets static/literal imports, not arbitrary future runtime fetch logic; reviewers must still check publication changes.

The website intentionally has no published product records yet. This guide prepares an approval workflow for real BODICH model photos and descriptions. Provisional categories and AI concept art must never be presented as confirmed stock or product photography.

## Approval checklist

1. Collect an authoritative BODICH manufacturer document, official page, or reviewable internal company reference. Verify that the proposed name, category and bilingual summaries are supported. Record the reference and the actual verification date in the intake JSON. A filled sourceReference field is not by itself proof of authenticity.
2. Obtain permission to publish the photograph: document ownership or a license, check model identity, remove private EXIF/location metadata, and optimize for web. The source must be a genuine approved BODICH product photo, not a concept render, logo or a competitor image.
3. **Do not commit any photo to `public/` before company sign-off.** Astro publishes every file under `public/` even if no product references it. Stage candidate images outside the repository; copy one candidate's files into `public/images/catalog/<model-slug>/` temporarily for local intake only, and remove them afterwards unless approved. **Stage and validate only one unpublished candidate at a time**: other staged photos will trigger the unreferenced-file gate. Never `git add` an unapproved photo. The normal `npm run check` rejects any unreferenced catalog photo. Remove hidden files such as Finder's `.DS_Store` and deliberate placeholders such as `.gitkeep` from this directory before validating: Git can ignore them, but Astro still copies files from `public/`. After sign-off, commit the approved photo **together with** its confirmed product record. No-photo records can omit `image` and show the localized fallback.
4. Copy intake-template.json to a **local untracked location** such as /tmp/model-review.json. Fill its required id, slug, existing categoryId, both language descriptions, and verification.sourceReference and verification.confirmedOn (YYYY-MM-DD, not in the future).
5. If adding a photo, add an `image` object with fields: `src` (for example `/images/catalog/<model-slug>/front.webp`), `alt` (object with `en` and `ro` strings), `width` and `height` (actual positive integer pixel dimensions). File names/directories use lowercase letters, digits, `_` and `-`, with no dots except the lowercase `.png`, `.jpg`, `.jpeg` or `.webp` extension. No doubled slashes. All files must be regular files, **5 MiB or smaller**, and free of common EXIF/GPS/XMP/text chunks. JPEG dimensions are read from raw headers; normalize the orientation and **strip all metadata before the file is staged**. Recommended: export/re-encode a clean copy in an image editor, inspect it, and remove EXIF/IPTC/comments with a trusted metadata tool (for example, `exiftool -all= -overwrite_original file.jpg` on a disposable copy). JPEGs must also have a proper EOI marker at the end of the file; extra bytes after EOI (including padding or camera-added data) are rejected. Nonstandard APPn/JPGn segments, repeated JFIF/Adobe/ICC blocks, JFXX thumbnails, oversized or multipart ICC profiles, and JFIF thumbnails are rejected as potentially private metadata. JPEG structural segments (DQT, DHT, DAC, DRI, DNL and SOS) must have valid internal lengths and table structure; malformed segments are rejected. ICC profiles are checked for basic envelope structure only; private text, copyright information, or identifiers can still be embedded in ICC tag payloads or padding. Prefer re-exporting without any ICC profile (or with a trusted standard sRGB profile), without embedded thumbnails, and re-encoding to remove trailing data. Metadata detection is defense-in-depth, not a guarantee of sanitization.
6. Run: `npm run catalog:intake -- /tmp/model-review.json`. It checks shape, unknown JSON keys, nonfuture date, IDs/slugs unique against already confirmed records, translations, photo path, file presence, **actual raster header dimensions**, common private metadata and file-size cap. `npm run check` additionally rejects **unreferenced** files in `public/images/catalog/`. A passing result never attests to source authenticity, photo rights, completeness of metadata removal or factual accuracy; manual inspection and image export hygiene are still required.
7. Have an authorized company reviewer verify the evidence, photo rights and localized copy. Do not commit confidential documents or internal evidence to a public GitHub repository.
8. Only after sign-off, copy the validated JSON product object as a TypeScript object into the confirmedProducts array in src/catalog/data.ts between BEGIN CONFIRMED PRODUCTS and END CONFIRMED PRODUCTS.
9. Run `npm run check`, `npm run build` and `node scripts/validate-catalog.mjs --routes dist`, then open a review PR. The product card and both localized detail URLs are generated automatically from the confirmed record.

## Explicitly out of scope

The published site must not invent or infer products, prices, performance specifications, certification, stock, warranty or delivery details. No payment or order flow is enabled. Final tests on physical devices and Safari/Firefox and the native Romanian copy pass are deferred to prelaunch.

The checked-in intake template has deliberately blank required fields, including `categoryId`; it is not a product and cannot pass validation until the actual category and authoritative information are supplied. Temporary CI fixture products are generated only in disposable copies for testing.
