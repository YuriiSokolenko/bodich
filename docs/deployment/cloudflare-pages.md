### HTML meta-refresh navigation policy (issue #75)

The Pages release gate uses parse5 with HTML5 parsing and decoded attributes to inspect `meta[http-equiv=refresh]` across the document, including `noscript` (with scripting disabled) and recursively nested `template` content. Refresh navigation is **denied by default**, even for relative or same-origin links. The **only** approved instance is a single `<meta http-equiv="refresh" content="0;url=/en/">` directly in the root document's `<head>` of **dist/index.html**, which is emitted by `Astro.redirect(hrefFor('en', 'home'))`. With `ASTRO_BASE=/bodich-preview`, only `content="0;url=/bodich-preview/en/"` is allowed in that same location. Element/attribute case differences and decoded HTML entities in the directive may be recognized, but the approved target and zero-delay `content` string must match exactly. No query, fragment, additional delay, external origin, second refresh, redirect on EN/RO routes, or refresh in templates/noscript is authorized. Obfuscated or ambiguous refresh instructions are rejected.

This static build-time check **does not replace runtime CSP, Cloudflare account/preview authorization, or a live-header validation**. It does not authorize deploying to production, opening previews to private materials, widening the route allow-list, or publishing the 132 unapproved supplier drafts. `public/_headers`, the release-safe profile and **NO-GO** status remain unchanged.

Astro currently renders the root language redirect in /index.html and ships EN/RO routes; no catch-all _redirects rules are approved. Any later redirect must be a reviewed exact rule, must preserve the canonical and hreflang target, and must pass the strict route gate. New image, font, PDF, 404.html, JavaScript directory or product routes are intentionally rejected until the committed release allow-list is independently amended; adding an asset to dist/ is not approval. Without a verified SITE_URL Astro deliberately omits canonical and alternate absolute URLs. For approved production, set SITE_URL to that verified HTTPS origin only and re-run full checks; sitemap.xml remains empty and robots.txt disallows crawl while all editorial gates are pending. Update the committed sitemap allow-list and release gate only in a *separate* human-reviewed public launch PR. A noindex tag cannot conceal accidental publication of private data.

public/_headers supplies static Cloudflare Pages CSP, nosniff, Referrer-Policy, frame protection and a **site-wide temporary noindex rule**. The global /* rule also applies to any future custom production hostname: the eventual launch PR must explicitly remove or scope noindex and update this verifier only after signed editorial publication approval. It is NOT preview-host-only today. Astro Vite inline threshold is zero and pages:verify rejects executable inline scripts so the self-only CSP does not break the mobile menu. These directives do not apply to Pages Functions or off-platform redirects. Do not enable HSTS in this shared file: it also affects preview hosts. For a verified production HTTPS domain only, the owner may introduce host-scoped Strict-Transport-Security after testing subdomain implications, redirect behavior, expiration and any includeSubDomains/preload decision. Confirm the **live** headers from the actual Pages preview and authorized production host using curl -sSI and preserve sanitized output alongside project ID, branch, commit SHA, URL and UTC timestamp in an owner-controlled evidence record. Validate 200/301, CSP, X-Content-Type-Options, Referrer-Policy, X-Robots-Tag and HTTPS. This issue cannot assert live evidence without account/URL authorization.

## Offline rehearsal, preview and rollback

1. On an isolated clean checkout of an approved commit, run npm ci, npm audit --audit-level=high, npm run check, npm run pages:self-test, npm run build, npm run pages:verify, npm run seo:routes and the CI Gitleaks scans. Save the digest manifest with the commit SHA. Repeat for the previous known-good commit in a *separate* directory. Verify that both builds produce only allow-listed routes and assets. The SHA-256 manifest is the immutable *local* artifact identity, not a Cloudflare deployment ID.
2. Once the account owner authorizes previews, restrict preview branch deployments to the approved source branch. Open a PR and capture the real unique *.pages.dev preview URL, its Cloudflare deployment ID, HTTP statuses and headers, crawl policy, navigation, translated routes, caching and security checks. Do not promote or bind a domain in this rehearsal; if preview authorization is unavailable, record **NO-GO (live rehearsal pending)** rather than claiming it passed.
3. On an authorized production deployment in the future, record the currently healthy Cloudflare **production deployment ID** before promotion. To reverse: in Workers & Pages > project > Deployments select the earlier **successful production** deployment, choose Rollback and confirm; **a preview deployment cannot be used as a rollback target**. Recheck the public hostname, selected production deployment ID, EN/RO routes, headers, sitemap and absence of draft material. A local dist/ checksum is not sufficient evidence of CDN state.
4. If content was exposed, immediately pause promotions, restrict access where possible, rollback, invalidate the affected Cloudflare zone/cache using the owner's approved cache-purge control, and verify affected URLs and edge regions. Rollback does not guarantee purge of existing edge-cached objects or third-party copies. Keep a timestamped sanitized incident record and re-run the checks before restoring traffic. No purge, rollback, DNS change or production deploy has been executed by this issue.
