## Cloudflare Pages settings and CI

Node version: .nvmrc = 24; use npm ci with the committed lockfile. Framework preset Astro; build command:
~~~
npm ci && npm run check && npm run build && npm run pages:verify && npm run catalog:products:dist && npm run catalog:reconcile:routes && npm run seo:routes && npm run media:public
~~~
Build output directory: dist. Keep SITE_URL unset for unapproved previews. Public release and Pages previews use the *release_safe* media profile; never use npm run build:beta, media:stage-beta or media:stage-private as a Cloudflare Pages command. No deployment secrets are required. The GitHub workflow Pages release security separately performs a pinned-image Gitleaks Git-history scan, source checks, npm audit of high/critical dependencies, static artifact scan, approved URL/sitemap scan and a non-root path smoke test. Require this check in main branch protection before authorizing future deployments. The manifest at visual-qa/pages-release-evidence.json lists only filenames and SHA-256 digests, not the private SKU content.

Astro currently renders the root language redirect in /index.html and ships EN/RO routes; no catch-all _redirects rules are approved. Any later redirect must be a reviewed exact rule, must preserve the canonical and hreflang target, and must pass the strict route gate. Without a verified SITE_URL Astro deliberately omits canonical and alternate absolute URLs. For approved production, set SITE_URL to that verified HTTPS origin only and re-run full checks; sitemap.xml remains empty and robots.txt disallows crawl while all editorial gates are pending. Update the committed sitemap allow-list and release gate only in a *separate* human-reviewed public launch PR. A noindex tag cannot conceal accidental publication of private data.

public/_headers supplies static Cloudflare Pages CSP, nosniff, Referrer-Policy, frame protection and a preview noindex tripwire. These directives do not apply to Pages Functions or off-platform redirects. Do not enable HSTS in this shared file: it also affects preview hosts. For a verified production HTTPS domain only, the owner may introduce host-scoped Strict-Transport-Security after testing subdomain implications, redirect behavior, expiration and any includeSubDomains/preload decision. Confirm the **live** headers from the actual Pages preview and authorized production host using curl -sSI and preserve sanitized output alongside project ID, branch, commit SHA, URL and UTC timestamp in an owner-controlled evidence record. Validate 200/301, CSP, X-Content-Type-Options, Referrer-Policy, X-Robots-Tag and HTTPS. This issue cannot assert live evidence without account/URL authorization.

## Offline rehearsal, preview and rollback

1. On an isolated clean checkout of an approved commit, run npm ci, npm audit --audit-level=high, npm run check, npm run pages:self-test, npm run build, npm run pages:verify, npm run seo:routes and the CI Gitleaks scans. Save the digest manifest with the commit SHA. Repeat for the previous known-good commit in a *separate* directory. Verify that both builds produce only allow-listed routes and assets. The SHA-256 manifest is the immutable *local* artifact identity, not a Cloudflare deployment ID.
2. Once the account owner authorizes previews, restrict preview branch deployments to the approved source branch. Open a PR and capture the real unique *.pages.dev preview URL, its Cloudflare deployment ID, HTTP statuses and headers, crawl policy, navigation, translated routes, caching and security checks. Do not promote or bind a domain in this rehearsal; if preview authorization is unavailable, record **NO-GO (live rehearsal pending)** rather than claiming it passed.
3. On an authorized production deployment in the future, record the currently healthy Cloudflare **production deployment ID** before promotion. To reverse: in Workers & Pages > project > Deployments select the earlier **successful production** deployment, choose Rollback and confirm; **a preview deployment cannot be used as a rollback target**. Recheck the public hostname, selected production deployment ID, EN/RO routes, headers, sitemap and absence of draft material. A local dist/ checksum is not sufficient evidence of CDN state.
4. If content was exposed, immediately pause promotions, restrict access where possible, rollback, invalidate the affected Cloudflare zone/cache using the owner's approved cache-purge control, and verify affected URLs and edge regions. Rollback does not guarantee purge of existing edge-cached objects or third-party copies. Keep a timestamped sanitized incident record and re-run the checks before restoring traffic. No purge, rollback, DNS change or production deploy has been executed by this issue.
